# misteRus Dashboard Cards

Учебный SPA-дашборд для управления банковскими картами. Проект показывает список карт, позволяет выбирать активную карту, блокировать и разблокировать её, делать быстрые переводы между своими картами в одной валюте, смотреть историю операций, фильтровать её и анализировать расходы и доходы по категориям.

Проект развивается от лабораторной к лабораторной. Актуальная лабораторная: **ЛР №7 «Типизация проекта на TypeScript»**.

Приложение не работает с реальным банком: все данные приходят с локального mock-сервера и хранятся в памяти процесса Node.js.

## О проекте

**misteRus Dashboard Cards** — это клиентское приложение на React, которое имитирует личный кабинет с банковскими картами. Основная задача проекта — показать осознанную работу с TypeScript в реальном React-приложении: типизацию домена, props, событий, состояния, API-ответов, ошибок и переиспользуемых абстракций.

Проект специально разделён на слои:

- `app` — настройка Redux Store.
- `pages` — страницы приложения.
- `components` — визуальные компоненты и составные блоки интерфейса.
- `features` — Redux-слайсы.
- `hooks` — переиспользуемая логика React.
- `shared` — типы, API, утилиты, конфигурация и общие UI-компоненты.
- `server` — mock-сервер на Express.

Приложение не требует авторизации, базы данных или внешних сервисов. Для запуска нужны только Node.js и npm.

## Возможности

### Карты

- Список банковских карт с балансом, типом и сроком действия.
- Поддержка типов карт: `Mir`, `Visa`, `MasterCard`.
- Выбор активной карты.
- Автоматический выбор первой карты, если сохранённая активная карта больше не существует.
- Блокировка и разблокировка карты.
- Сохранение активной карты в `localStorage`.
- Модальное окно с подробной информацией о карте.
- Маскирование номера карты: показываются только последние четыре цифры.

### Переводы

- Быстрый перевод между своими картами.
- Перевод только между картами в одной валюте.
- Перевод только с разблокированной карты.
- Перевод только на разблокированную карту.
- Запрет перевода на ту же самую карту.
- Проверка положительной суммы.
- Проверка достаточности средств.
- Округление суммы до копеек.
- Поддержка ввода суммы как с точкой, так и с запятой.
- Создание двух операций: списание с карты-источника и зачисление на карту-получателя.
- Сохранение суммы и карты-получателя в `localStorage`.
- Показ ошибок сервера в уведомлении.

### Операции

- Список операций по активной карте на главной странице.
- Полная история операций на отдельной странице.
- Фильтр операций: все, доходы, расходы.
- Сортировка операций от новых к старым.
- Сортировка по `createdAt`, если поле есть, иначе по `date`.
- Дополнительная сортировка по `id` при одинаковом времени.
- Модальное окно с деталями операции.
- Отображение даты и времени операции.
- Определение категории и иконки по названию операции.

### Аналитика

- Статистика по каждой карте: количество операций и итоговая сумма.
- Статистика по валютам: доходы и расходы отдельно.
- Диаграмма зачислений по категориям.
- Диаграмма расходов по категориям.
- Пересчёт долларовых операций в рубли для категорийных диаграмм по фиксированному курсу.
- Пустые состояния, если данных для статистики нет.

### Интерфейс и надёжность

- Две основные страницы и страница 404.
- Общая навигация и кнопка обновления данных.
- Индикаторы загрузки и фонового обновления.
- Единый компонент уведомлений для ошибок, предупреждений и успеха.
- Обработка сетевых ошибок.
- Повторный запрос данных по кнопке.
- Базовая доступность: клавиатурное управление картой, `aria`-атрибуты модального окна, закрытие по Escape.
- Адаптивная вёрстка на CSS без UI-библиотек.

## Быстрый старт

Установка зависимостей:

```bash
npm ci
```

`npm ci` рекомендуется использовать всегда, когда есть `package-lock.json`. Он ставит зависимости строго по lock-файлу. Команда `npm install` тоже работает, но может обновить lock-файл.

Запуск mock-сервера в первом терминале:

```bash
npm run server
```

Сервер будет доступен по адресу:

```text
http://localhost:3001
```

Запуск клиента во втором терминале:

```bash
npm run dev
```

Клиент будет доступен по адресу:

```text
http://localhost:5173
```

Без запущенного mock-сервера интерфейс загрузится, но данные карт и операций не придут, и приложение покажет ошибку загрузки.

Проверка production-сборки:

```bash
npm run build
npm run preview
```

`npm run build` сначала запускает `tsc`, затем собирает проект через Vite. Если в типах есть ошибка, сборка не начнётся.

## Конфигурация

### Адрес API

Адрес API задаётся в файле `src/shared/config/api.ts`:

```ts
export const API_URL = 'http://localhost:3001'
```

Если mock-сервер запущен на другом порту, нужно изменить это значение.

### Порт mock-сервера

По умолчанию сервер слушает порт `3001`:

```bash
npm run server
```

Можно переопределить порт через переменную окружения `PORT`.

Bash / WSL:

```bash
PORT=3002 npm run server
```

PowerShell:

```powershell
$env:PORT=3002; npm run server
```

После смены порта сервера не забудьте поменять `API_URL` в `src/shared/config/api.ts`.

### Курс доллара для диаграмм

В `src/shared/config/constants.ts` задан фиксированный курс:

```ts
export const USD_TO_RUB = 90
```

Он используется только для приведения долларовых операций к рублям при построении категорийных диаграмм. Это учебное упрощение, а не реальный финансовый курс.

### Переменные окружения

Отдельного `.env` в проекте нет. Все настройки находятся в исходном коде или передаются серверу через `PORT`.

## Архитектура

Проект построен по слоям:

```text
src/app                     настройка Redux Store
src/pages                   страницы и композиция блоков
src/components              визуальные компоненты
src/features                Redux-слайсы
src/hooks                   переиспользуемая React-логика
src/shared/api              Axios, RTK Query, guard-функции, ошибки
src/shared/config           адрес API и константы
src/shared/lib              чистые утилиты и расчёты
src/shared/types            доменные типы
src/shared/ui               общие UI-компоненты
server                      mock API на Express
```

Направление зависимостей в целом такое:

```text
pages -> components -> shared/ui
pages -> hooks -> shared/api, shared/lib, shared/types
components -> shared/lib, shared/types, shared/ui
features -> shared/types
shared/* -> не импортирует pages и components
server/* -> независимый mock backend
```

Поток данных:

```text
server/index.js
    |
    v
Axios apiClient
    |
    v
RTK Query bankApiSlice
    |
    v
useBankData / useActiveCard
    |
    v
pages и components
    |
    v
Redux Store и локальное состояние компонентов
```

Более подробно запрос проходит так:

1. Компонент или хук вызывает `useGetCardsQuery` или `useGetOperationsQuery`.
2. RTK Query вызывает `axiosBaseQuery`.
3. `axiosBaseQuery` вызывает generic-функцию `request<T>`.
4. `request<T>` делает запрос через `apiClient.request<T>` и возвращает `result.data`.
5. `transformResponse` получает ответ как `unknown`.
6. Guard-функция `isCardArray` или `isOperationArray` проверяет структуру данных.
7. Если структура неверная, выбрасывается ошибка.
8. Если структура верная, данные кешируются RTK Query и попадают в компоненты.
9. После mutation RTK Query инвалидирует теги и повторно загружает нужные данные.

## Маршруты и страницы

| Путь | Компонент | Назначение |
| --- | --- | --- |
| `/` | `DashboardPage` | Карты, активная карта, перевод, операции по активной карте |
| `/operations` | `OperationsPage` | Полная история, статистика и диаграммы |
| `*` | `NotFoundPage` | Страница 404 |

Все страницы находятся внутри `Layout`, поэтому шапка, навигация, кнопка обновления и подвал общие.

`Layout` использует `useBankData`, чтобы показывать индикатор фонового обновления и запускать `refresh` для обеих коллекций. RTK Query дедуплицирует одинаковые запросы, поэтому вызов `useBankData` на странице и в `Layout` не создаёт лишнюю нагрузку.

## Пользовательские сценарии

### Главная страница

1. Пользователь открывает `/`.
2. Приложение загружает карты и операции.
3. Если карты есть, выбирается активная карта:
   - сохранённая в `localStorage`, если она существует;
   - иначе первая карта из списка.
4. Отображается список карт.
5. Отображается баланс активной карты.
6. Отображается форма быстрого перевода.
7. Отображается список операций активной карты с учётом фильтра.

### Блокировка карты

1. Пользователь нажимает «Заблокировать» на карте.
2. `CardItem` вызывает `onToggleBlock`.
3. `DashboardPage` вызывает mutation `toggleCardBlock`.
4. Сервер меняет `isBlocked` у карты.
5. RTK Query инвалидирует тег `Card`.
6. Список карт перезапрашивается.
7. Если ошибка, показывается предупреждение.

### Быстрый перевод

1. Пользователь выбирает карту-получателя.
2. Вводит сумму.
3. Нажимает «Перевести».
4. Клиент проверяет:
   - выбрана ли карта-источник;
   - не заблокирована ли она;
   - выбрана ли карта-получатель;
   - является ли сумма числом;
   - больше ли сумма нуля;
   - достаточно ли средств.
5. Клиент отправляет `POST /api/transfers`.
6. Сервер повторно проверяет все правила.
7. Сервер меняет балансы и создаёт две операции.
8. RTK Query инвалидирует теги `Card` и `Operation`.
9. Список карт и операций обновляется.
10. Пользователь видит уведомление об успехе.

### Фильтрация операций

1. Пользователь выбирает «Все», «Доходы» или «Расходы».
2. `filterSlice` сохраняет значение в Redux и `localStorage`.
3. `useActiveCard` фильтрует операции активной карты.
4. `OperationsPage` фильтрует все операции.
5. Сортировка применяется после фильтрации.

Доход — операция с `amount > 0`. Расход — операция с `amount < 0`.

### Детали операции

1. Пользователь нажимает на операцию в истории.
2. Открывается `TransactionDetails`.
3. Показываются название, сумма, дата и время, карта, тип операции и категория.
4. Модальное окно закрывается по кнопке, клику по overlay или клавише Escape.

### Обновление данных

1. Пользователь нажимает «Обновить данные».
2. `Layout` вызывает `refresh`.
3. `useBankData` вызывает `refetchCards` и `refetchOperations`.
4. Пока идёт запрос, показывается индикатор «Обновление...».

### Ошибка загрузки

1. Если сервер недоступен, RTK Query возвращает ошибку.
2. `useBankData` объединяет `isError` для карт и операций.
3. Страница показывает `NoticeBanner` с кнопкой «Повторить».
4. Повторный запрос вызывает `refresh`.

## Данные и типы

Основные типы описаны в `src/shared/types/index.ts`.

### `Card`

```ts
export interface Card {
  id: number
  number: string
  balance: number
  currency: string
  isBlocked: boolean
  expiry: string
  type: 'Mir' | 'Visa' | 'MasterCard'
}
```

Поле `type` — union из трёх строковых литералов. Это не просто `string`: компилятор не даст передать сюда произвольное значение.

### `Operation`

```ts
export interface Operation {
  id: number
  cardId: number
  title: string
  amount: number
  date: string
  createdAt?: string
}
```

`createdAt` необязателен, потому что старые операции могут иметь только `date`. Новые переводы получают и `date`, и `createdAt`.

### `FilterValue`

```ts
export type FilterValue = 'all' | 'income' | 'expense'
```

Используется в Redux, фильтре и списке операций. Благодаря union нельзя случайно передать значение, которого нет в фильтре.

### Утилитарные типы

```ts
export type CardBalanceInfo = Pick<Card, 'balance' | 'currency' | 'isBlocked'>

export type NewOperation = Omit<Operation, 'id'>

export type CardWithStats = Card & {
  opsCount: number
  total: number
}
```

- `Pick` используется в `BalanceWidget`: виджету нужны только баланс, валюта и признак блокировки.
- `Omit` используется в `QuickTransfer`: клиент формирует операцию без `id`, потому что `id` назначает сервер.
- `Record` используется в `operationsStats.ts` для группировки статистики по категориям и валютам.
- `&` используется в `CardWithStats`: карта дополняется полями статистики.

### Состояния загрузки и перевода

```ts
export type LoadingState =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success' }
  | { status: 'error'; message: string }
```

```ts
type TransferState =
  | { status: 'idle' }
  | { status: 'submitting' }
  | { status: 'success'; message: string }
  | { status: 'error'; message: string }
```

Это discriminated union: поле `status` является меткой, по которой TypeScript сужает тип. Например, `message` существует только в состояниях `success` и `error`, и компилятор не даст прочитать его без проверки `status`.

### Дополнительные типы

```ts
export interface TransferPayload {
  fromCardId: number
  toCardId: number
  amount: number
}

export interface TransferResult {
  fromCard: Card
  toCard: Card
  operations: Operation[]
}
```

`TransferPayload` описывает тело запроса на перевод. `TransferResult` — успешный ответ сервера.

### `POST /api/transfers`

Пример тела запроса:

```json
{
  "fromCardId": 1,
  "toCardId": 2,
  "amount": 1500.5
}
```

Успешный ответ:

```json
{
  "fromCard": {},
  "toCard": {},
  "operations": []
}
```

В реальном ответе `fromCard` и `toCard` содержат обновлённые карты, а `operations` — две созданные операции.

Сервер проверяет:

- `fromCardId` и `toCardId` являются числами;
- `amount` является конечным числом;
- `amount > 0`;
- карты существуют;
- нельзя переводить на ту же карту;
- валюты карт совпадают;
- карта-источник не заблокирована;
- карта-получатель не заблокирована;
- на карте-источнике достаточно средств.

При ошибке сервер возвращает `400` или `404` и объект:

```json
{
  "error": "Текст ошибки"
}
```

### Клиент API

`src/shared/api/client.ts` создаёт Axios instance:

- `baseURL` берётся из `API_URL`;
- заголовок `Accept: application/json`;
- request interceptor логирует метод и URL;
- response interceptor логирует статус и URL ошибки.

### RTK Query

`src/shared/api/bankApiSlice.ts` содержит:

- `getCards`;
- `getOperations`;
- `toggleCardBlock`;
- `createTransfer`.

Для запросов используется собственный `axiosBaseQuery`, потому что проект работает с Axios напрямую, а не через встроенный `fetchBaseQuery`.

Generic-функция запроса:

```ts
const request = async <T,>({ url, method, data }: AxiosQueryArgs): Promise<T> => {
  const result = await apiClient.request<T>({ url, method, data })
  return result.data
}
```

Она возвращает `Promise<T>` и позволяет типизировать результат запроса.

### Теги RTK Query

`getCards` предоставляет теги:

- `{ type: 'Card', id }` для каждой карты;
- `{ type: 'Card', id: 'LIST' }` для списка.

`getOperations` предоставляет аналогичные теги для операций.

Мутации инвалидируют списки, поэтому после блокировки или перевода RTK Query автоматически запрашивает свежие данные.

## Валидация внешних данных

Данные из API нельзя считать доверенными, даже если это собственный mock-сервер. Поэтому в проекте используется подход `unknown` + type guard.

`transformResponse` получает ответ как `unknown`:

```ts
transformResponse: (response: unknown) => {
  if (!isCardArray(response)) {
    throw new Error('Invalid response format for cards')
  }
  return response
}
```

Guard-функции находятся в `src/shared/api/guards.ts`:

- `isCardArray`;
- `isOperationArray`.

`isCardArray` проверяет:

- что значение является массивом;
- что каждый элемент является объектом;
- что `id`, `balance` — числа;
- что `number`, `currency`, `expiry` — строки;
- что `isBlocked` — boolean;
- что `type` — одно из `Mir`, `Visa`, `MasterCard`.

`isOperationArray` проверяет:

- что значение является массивом;
- что `id`, `amount`, `cardId` — числа;
- что `title`, `date` — строки;
- что `createdAt` либо отсутствует, либо является строкой.

Если структура не совпадает, запрос завершается ошибкой, а не отдаёт в приложение частично неверные данные.

Ошибки API обрабатываются отдельно:

- `isAxiosError` определяет ошибку Axios;
- `getApiErrorMessage` безопасно извлекает `error` из ответа;
- если текст ошибки не найден, используется fallback-сообщение.

## Ограничения и технический долг

- Mock-сервер хранит данные в памяти. После перезапуска сервера карты и операции возвращаются к исходному состоянию.
- Нет реальной аутентификации и авторизации.
- Нет базы данных.
- Нет реального банковского API.
- Переводы возможны только между картами в одной валюте.
- Конвертация валют не поддерживается.
- Курс `USD_TO_RUB` фиксированный и используется только для диаграмм.

## Основная теория для ответов

### Зачем нужен TypeScript

TypeScript — это надмножество JavaScript, которое добавляет статическую типизацию. Типы проверяются на этапе компиляции и стираются во время выполнения. Это значит, что TypeScript помогает найти ошибки до запуска приложения, но не заменяет проверку внешних данных во время работы.

В проекте TypeScript используется для:

- описания доменных сущностей;
- типизации props и callbacks;
- типизации событий формы;
- типизации состояния;
- типизации API-ответов и ошибок;
- создания переиспользуемых generic-абстракций;
- включения строгих проверок компилятора.

### `type` и `interface`

`interface` удобно использовать для описания объектов и расширения через `extends`.

Пример из проекта:

```ts
interface ButtonProps extends ComponentProps<'button'> {
  children: ReactNode
}
```

`type` удобно использовать для union-типов, утилитарных типов и пересечений.

Примеры из проекта:

```ts
type FilterValue = 'all' | 'income' | 'expense'

type LoadingState =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success' }
  | { status: 'error'; message: string }

type NewOperation = Omit<Operation, 'id'>

type CardWithStats = Card & {
  opsCount: number
  total: number
}
```

Оба подхода допустимы. Главное — использовать их осознанно и не дублировать одну и ту же структуру без причины.

### Union-типы

Union-тип означает, что значение может быть одним из нескольких вариантов.

```ts
type FilterValue = 'all' | 'income' | 'expense'
```

Если попытаться передать `'other'`, компилятор выдаст ошибку. Это защищает от опечаток и неверных значений.

### Discriminated union

Discriminated union — это union объектов, у которых есть общее поле-метка. В проекте это поле `status`.

```ts
type TransferState =
  | { status: 'idle' }
  | { status: 'submitting' }
  | { status: 'success'; message: string }
  | { status: 'error'; message: string }
```

TypeScript умеет сужать тип по значению `status`. В ветке `if (transferState.status === 'error')` компилятор точно знает, что у объекта есть `message`.

### Generics

Generic позволяет сохранить связь между входным и выходным типом, не теряя конкретику.

```ts
export function useLocalStorage<T>(
  key: string,
  initialValue: T
): [T, (value: T) => void]
```

Если вызвать `useLocalStorage<string>`, то и значение, и сеттер будут работать со строкой.

Generic-запрос:

```ts
const request = async <T,>({ url, method, data }: AxiosQueryArgs): Promise<T> => {
  const result = await apiClient.request<T>({ url, method, data })
  return result.data
}
```

`Promise<T>` означает, что после `await` будет значение типа `T`.

### Utility types

`Pick<T, K>` создаёт тип только с выбранными полями:

```ts
type CardBalanceInfo = Pick<Card, 'balance' | 'currency' | 'isBlocked'>
```

`Omit<T, K>` создаёт тип без указанных полей:

```ts
type NewOperation = Omit<Operation, 'id'>
```

`Record<K, V>` создаёт объект с ключами типа `K` и значениями типа `V`:

```ts
const statsByCategory: Record<string, CategoryStat> = {}
```

### `unknown` и `any`

`any` отключает проверку типов. С `any` можно вызвать любое свойство, и компилятор не поможет.

`unknown` означает «значение неизвестного типа». Его нельзя использовать напрямую, пока не выполнено сужение типа.

В проекте данные API приходят как `unknown`:

```ts
transformResponse: (response: unknown) => {
  if (!isCardArray(response)) {
    throw new Error('Invalid response format for cards')
  }
  return response
}
```

Guard-функция — это функция, которая проверяет значение и возвращает type predicate:

```ts
export const isCardArray = (data: unknown): data is Card[] => {
  // проверки
}
```

После успешной проверки TypeScript знает, что `data` — это `Card[]`.

### `strict` и проверки на `null`

`strict` включает набор строгих проверок, включая `strictNullChecks`. Без него `null` и `undefined` могут неявно попадать туда, где ожидается объект.

В проекте есть проверки:

- `if (!card) return null`;
- `if (!activeCard) return`;
- `card?.currency`;
- `getCardById` возвращает `Card | undefined`;
- `TransactionDetails` принимает `card: Card | undefined`.

### `noUncheckedIndexedAccess`

Флаг `noUncheckedIndexedAccess` делает обращение по индексу потенциально опасным:

```ts
const firstCard = cards[0] // Card | undefined
```

Поэтому код обязан проверить значение перед использованием. В проекте это видно в `useActiveCard`, `QuickTransfer`, `CategoryPieChart` и `operationsStats`.

### `noUnusedLocals` и `noUnusedParameters`

Эти флаги не дают оставлять неиспользуемые переменные и параметры. Они помогают поддерживать код в чистоте и убирать мёртвый код.

### Типизация React props

Props описываются через `interface` или `type`:

```ts
interface CardItemProps {
  card: Card
  isActive: boolean
  onSelect: (id: number) => void
  onToggleBlock: (id: number) => Promise<void>
  onShowDetails: (card: Card) => void
}
```

Callback типизируется как функция:

```ts
onSelect: (id: number) => void
```

Это значит, что обработчик обязан принимать число и не обязан возвращать значение.

### Типизация событий

В React события имеют свои типы:

```ts
const handleAmountChange = (e: ChangeEvent<HTMLInputElement>) => {
  setAmount(e.target.value)
}
```

`e.target.value` у `HTMLInputElement` всегда строка. Поэтому сумма хранится как `string`, а число получается через `Number(...)` после проверки.

### Типизация состояния

Если TypeScript не может вывести тип или вывод неочевиден, используется generic:

```ts
const [selectedCard, setSelectedCard] = useState<Card | null>(null)
const [blockError, setBlockError] = useState<string | null>(null)
const [transferState, setTransferState] = useState<TransferState>({ status: 'idle' })
```

### `ReactNode` и `ComponentProps`

`ReactNode` описывает любой React-контент: элемент, строку, число, фрагмент, массив, `null`.

`ComponentProps<'button'>` описывает все props нативной кнопки. Это лучше, чем вручную перечислять `onClick`, `disabled`, `type`, `className` и другие атрибуты.

### `Promise<T>` и обработка ошибок

Функция, которая возвращает `Promise<T>`, после `await` даёт значение типа `T`.

```ts
const request = async <T,>(...): Promise<T> => {
  const result = await apiClient.request<T>(...)
  return result.data
}
```

Ошибки обрабатываются как `unknown`:

```ts
catch (error: unknown) {
  setTransferState({
    status: 'error',
    message: getApiErrorMessage(error, 'Не удалось выполнить перевод'),
  })
}
```

Сначала ошибка проверяется, и только потом из неё извлекается сообщение. Это безопаснее, чем сразу приводить ошибку к `any`.

### React, Redux и RTK Query в этом проекте

- React отвечает за отображение и локальное состояние компонентов.
- Redux Toolkit хранит активную карту и фильтр.
- RTK Query загружает данные, кеширует их и обновляет после mutations.
- `useBankData` объединяет два запроса в один удобный интерфейс.
- `useActiveCard` связывает Redux-состояние активной карты с операциями.

### 5. Число из поля формы: строка, `ChangeEvent<HTMLInputElement>`, проверка

**Что сделано**

- Сумма перевода хранится как `string`.
- Используется `ChangeEvent<HTMLInputElement>`.
- Значение приводится к числу через `Number(...)`.
- Проверяется пустая строка.
- Проверяется `Number.isFinite`.
- Проверяется `amount > 0`.
- Проверяется достаточность средств.
- Сумма округляется до копеек.

**Что показать**

Открыть `src/components/QuickTransfer.tsx`:

```ts
const [amount, setAmount] = useLocalStorage<string>('last_transfer_amount', '')

const handleAmountChange = (e: ChangeEvent<HTMLInputElement>) => {
  setAmount(e.target.value)
  resetStatus()
}

const normalizedAmount = amount.replace(',', '.').trim()
const numericAmount = Number(normalizedAmount)

if (!normalizedAmount || !Number.isFinite(numericAmount) || numericAmount <= 0) {
  setTransferState({
    status: 'error',
    message: 'Введите корректную сумму больше нуля',
  })
  return
}
```

Также показать input:

```tsx
<input
  type="text"
  inputMode="decimal"
  value={amount}
  onChange={handleAmountChange}
/>
```

**Теория**

Значение любого текстового поля в браузере — строка. Даже `type="number"` в React возвращает строку. Поэтому нельзя просто сказать «это число». Нужно привести значение к числу и проверить его. `Number.isFinite` отсекает `NaN`, `Infinity` и `-Infinity`.

### 6. `npm run typecheck` проходит без ошибок, `any` и `@ts-ignore` отсутствуют

**Что сделано**

- В коде нет `any`.

### 1. Утилиты типов `Pick`, `Omit` и `Record` на своём домене

- `Omit` — `NewOperation` для создания операции без ID.

`src/shared/types/index.ts`:


### 2. Состояние загрузки описано union и разбирается по значению

**Что сделано**

- `LoadingState` описан как discriminated union.
- `DashboardPage` формирует состояние по `isLoading`, `isError`, `hasData`.
- Компоненты проверяют `status` перед использованием `message`.
- `TransferState` использует тот же подход.

**Что показать**

`src/shared/types/index.ts`:

```ts
export type LoadingState =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success' }
  | { status: 'error'; message: string }
```

`src/pages/DashboardPage.tsx`:

```ts

  : isError

    : hasData
      ? { status: 'success' }
      : { status: 'idle' }
```

Показать разбор:

```ts

  // ...
}
```

**Теория**

Union из объектов с общим полем-меткой называется discriminated union. Компилятор использует метку для сужения типа. Это лучше, чем набор независимых boolean-флагов, потому что невозможно одновременно находиться в состояниях `loading` и `error` без явного описания такого варианта.

### 3. Осознанный выбор `type` и `interface`, расширение через `extends` и `&`

**Что сделано**

- `interface` используется для объектов: `Card`, `Operation`, `TransferPayload`, `TransferResult`, props компонентов.
- `type` используется для union, utility types и пересечений.
- `ButtonProps extends ComponentProps<'button'>`.
- `CardWithStats = Card & { opsCount, total }`.

**Что показать**

`src/shared/ui/Button.tsx`:

```ts

  children: ReactNode
}
```

`src/shared/types/index.ts`:

```ts

  opsCount: number
  total: number
}
```

Объяснить:

- `extends` расширяет интерфейс;
- `&` создаёт пересечение типов;
- `type` удобен для union и utility types;
- `interface` удобен для объектных моделей и расширения.

**Теория**

`interface` и `type` во многом взаимозаменяемы, но есть различия. `interface` можно расширять через `extends` и объединять декларациями. `type` лучше подходит для union, intersections и утилитарных преобразований. В проекте выбор сделан по назначению типа, а не случайно.

### 5. Данные из API принимаются как `unknown` и проверяются, а не `as`

**Что сделано**

- `transformResponse` принимает `response: unknown`.
- `isCardArray` и `isOperationArray` проверяют структуру.
- В API-слое нет приведения ответа через `as Card[]` или `as Operation[]`.
- Ошибки обрабатываются через `isAxiosError`.
- Текст ошибки извлекается через `getApiErrorMessage`.

**Что показать**

`src/shared/api/bankApiSlice.ts`:

```ts
transformResponse: (response: unknown) => {
  if (!isCardArray(response)) {
    throw new Error('Invalid response format for cards')
  }
  return response
}
```

`src/shared/api/guards.ts`:

```ts
export const isCardArray = (data: unknown): data is Card[] => {
  if (!Array.isArray(data)) return false
  return data.every((item) => {
    // проверка полей
  })
}
```

`src/shared/api/errors.ts`:

```ts
export const getApiErrorMessage = (
  error: unknown,
  fallback: string
): string => {
  // безопасное извлечение сообщения
}
```

**Теория**

`as` — это утверждение типа. Оно не проверяет данные во время выполнения, а только говорит компилятору «поверь мне». Если API вернёт другую структуру, приложение может упасть. `unknown` заставляет сначала проверить данные. Type guard возвращает `data is Card[]`, после чего TypeScript доверяет проверке.

Важно: в проекте остаются два приведения, не связанные с API:

- `JSON.parse(item) as T` внутри generic-хука `useLocalStorage`;
- `document.getElementById('root') as HTMLElement` в точке входа.

Это не ответы API. Для API используется проверка через `unknown` и guard-функции.

### 1. Свой generic, полезный в проекте: `useLocalStorage<T>`

**Что сделано**

```ts
  key: string,
  initialValue: T
```

## Возможные вопросы преподавателя

### Почему не `any`?

`any` отключает проверку типов и позволяет ошибке проявиться только во время выполнения. В проекте вместо `any` используются конкретные типы, `unknown` и type guards.

### Чем `unknown` лучше `any`?

`unknown` требует сначала проверить значение. `any` разрешает делать с ним что угодно без проверки. Для внешних данных `unknown` безопаснее.

### Почему не использовать `as` для ответа API?

`as` не проверяет данные во время выполнения. Если сервер вернёт другую структуру, приложение упадёт. Guard-функция действительно проверяет поля и только потом сужает тип.

### Чем `type` отличается от `interface`?

`interface` удобен для объектных моделей и расширения через `extends`. `type` удобен для union, intersections, utility types и алиасов. В проекте оба используются по назначению.

### Что такое discriminated union?

Это union объектов с общим полем-меткой, например `status`. По значению метки TypeScript сужает тип и разрешает доступ только к полям конкретного варианта.

### Зачем нужен generic `useLocalStorage<T>`?

Он сохраняет связь между типом значения и типом сеттера. Нельзя случайно записать в строковое значение число или объект.

### Зачем `Promise<T>`?

Он показывает, какой тип будет после `await`. В проекте `request<T>` возвращает `Promise<T>`, поэтому результат запроса типизирован.

### Что делает `noUncheckedIndexedAccess`?

Он делает результат индексации `T | undefined`. Код обязан проверить значение перед использованием. Это защищает от выхода за границы массива и отсутствующих ключей.

### Почему TypeScript версии 6, а не 7?

`typescript-eslint@8.72.1` поддерживает TypeScript в диапазоне `>=4.8.4 <6.1.0`. TypeScript 7 несовместим с текущей версией линтера. Для стабильной проверки типов и линтинга используется TypeScript 6.

### Что будет, если API вернёт неверные данные?

`transformResponse` получит `unknown`, guard-функция вернёт `false`, и запрос завершится ошибкой. В интерфейсе появится уведомление, а не частично неверные данные.

### Где хранится состояние?

Глобальное состояние — в Redux Store: активная карта и фильтр. Данные API — в кеше RTK Query. Локальное состояние компонентов — в `useState`. Часть пользовательских настроек — в `localStorage`.

### Почему `useBankData` вызывается в нескольких местах?

RTK Query дедуплицирует одинаковые запросы и использует кеш. Это позволяет `Layout` и страницам независимо получать одни и те же данные без дублирования сетевых запросов.

### Как обновляются данные после перевода?

Mutation `createTransfer` инвалидирует теги `Card/LIST` и `Operation/LIST`. RTK Query автоматически повторно загружает карты и операции, поэтому балансы и история обновляются без ручного перезапуска.
